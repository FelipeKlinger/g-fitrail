Propósito y Visión del Producto

El Problema Detectado

Los gimnasios tradicionales sufren de fragmentación: usan un software para cobros, Excel para reservas y WhatsApp para atención. Esto genera descontrol y mala experiencia de usuario.

La Solución: Fitrail

Una plataforma web centralizada diseñada en torno a 3 roles clave:

  • Administrador: Panel de métricas y CRUD global.
  • Entrenador: Gestión de tiempo, clases y seguimiento físico.
  • Cliente: Autonomía total (pagos, reservas, evolución).

Metodología y Trabajo de Equipo

Al ser un equipo de 4 personas, la coordinación fue el pilar fundamental para no pisarnos el código y avanzar en paralelo.

División del Trabajo

Estructuramos el proyecto en 4 áreas core: Base de datos, Lógica MVC (Controladores), Vistas UI/UX, e Integraciones de terceros.

Control de Versiones

Uso estricto de ramas en Git (Feature Branches). Nadie subía a main sin que otro compañero revisara el código (Pull Requests).

Entorno Homogéneo

Implementamos Docker + Makefile. Así los 4 trabajamos con las mismas versiones de PHP y MySQL, evitando el "en mi máquina sí funciona".

Arquitectura del Sistema

Patrón MVC y Seguridad

Desarrollado sobre Laravel 12. La seguridad se gestiona a través de Middlewares que interceptan las peticiones y redirigen según el rol (Admin, Client, Entrenador).

Frontend Utilitario

Uso intensivo de Tailwind CSS para mantener un diseño oscuro y coherente, junto con Alpine.js para reactividad ligera sin sobrecargar el cliente.

Integraciones y APIs

Para no reinventar la rueda en áreas críticas, delegamos responsabilidades a servicios líderes del mercado.

Pagos (Stripe)

Gestión de suscripciones y pagos seguros. Utilizamos Webhooks para activar planes en la base de datos tras el pago exitoso.

CMS (Contentful)

CMS Headless para que la administración del gimnasio pueda cambiar textos e imágenes de la Landing Page sin tocar código.

Chatbot (Dialogflow)

Endpoint conversacional inteligente mediante la API de Google para responder dudas comunes de los clientes 24/7.

Modelo de Datos Transaccional

El diseño relacional fue la primera piedra angular del proyecto. Separamos la lógica de usuarios genéricos de los perfiles específicos.

Perfiles (1:1)

La tabla users maneja la autenticación. De ahí derivamos relaciones 1:1 estables hacia clients o entrenadors, permitiendo campos específicos sin ensuciar la auth.

Transacciones (Reservas)

La tabla reservas une Clientes con Entrenamientos. Implementamos un trigger por software que altera la "capacidad" del entrenamiento al reservar o cancelar.

Toma de Decisiones y Retos

1

Concurrencia en Reservas

El Problema: Evitar que dos clientes reserven la última plaza a la vez.
La Solución: Gestión atómica de la tabla Entrenamientos. Cuando se crea una reserva, se decrementa la capacidad; si se cancela, se incrementa. Validado mediante middlewares previos a la inserción.

2

Despliegue y Pruebas

El Problema: Testear el Webhook de Stripe en entorno local.
La Solución: Utilizamos Cloudflare Tunnels para exponer el servicio local de forma segura mediante HTTPS público sin necesidad de abrir puertos en el router.

Reflexión Crítica del Equipo

¿Qué nos funcionó muy bien?

  • La división de tareas evitó bloqueos; mientras unos hacían BD, otros avanzaban vistas.
  • La paleta de colores restringida (Tailwind) aceleró mucho el diseño frontend.
  • Usar Contentful le dio un acabado muy profesional al sistema sin añadir peso a la BD.

¿Qué mejoraríamos en el futuro?

  • Implementar Tests Automatizados (PHPUnit). En este MVP la verificación fue manual, lo que quita tiempo al final.
  • Refinar la gestión asíncrona de Stripe mediante Webhooks completos en vez de depender solo de redirecciones success/cancel.
